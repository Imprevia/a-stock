# 交易规则工程化

## Status

`active` · 版本 `0.1`

## 目标

为 A 股盘后研究建立一套可重复执行、可量化、可追溯并可接入 CI 的交易规则工程流程，使规则修改能够被机器验证，使每次判断都能定位到输入、规则版本、代码版本和逐规则执行证据。

## 角色

- 盘后研究者：使用固定快照或盘后数据运行规则，读取评分、置信度、否决和证据链。
- 规则维护者：修改 YAML 规则、阈值来源、文档解释和测试，接受 CI 门禁。
- 策略开发者：在后续阶段复用稳定规则输出，但不能把未验证阈值当成收益结论。
- 审核者：通过覆盖清单、Git diff、证据 manifest 和回放验证规则变更。

## 范围

- 规则事实源：版本化 YAML 注册表、闭合 schema、稳定 evaluator 名称和全库覆盖清单。
- 输入：规范化日频市场快照、可选分钟确认字段、provider 质量记录和可追溯人工事件。
- 执行：评分、权重、缺失处理、置信度、硬否决、环境分类和逐规则 trace。
- 验证：历史回放、样本内/样本外、成本、置信区间、生命周期和回滚证据。
- 自动化：离线 PR 门禁、盘后定时运行、Artifact 和月度哈希摘要。

不包含自动下单、券商连接、实盘账户控制、主体意图推断，也不保证任何经验阈值具有收益优势。

## 核心流程

1. 维护者修改规则 YAML、对应量化文档和测试 fixture。
2. PR CI 离线校验 schema、规则覆盖、文档映射、确定性输出、证据和 docs-contract。
3. 合并后盘后 workflow 获取并规范化真实数据；数据源异常时明确输出降级或数据不足。
4. 执行器对每条规则生成 trace，再由规则集聚合评分、否决、置信度和环境分类。
5. 证据生成器记录输入哈希、规则版本、Git SHA、provider 状态和结果哈希，并上传 Artifact。
6. 回测流程积累至少 500 个有效交易日、目标 750 日的证据后，才允许申请生命周期晋级。

## 业务规则

- YAML 是机器事实源；Markdown 是人读说明层，两者漂移必须由 CI 阻断。
- 规则 ID 稳定且全库唯一；版本、输入、阈值或 evaluator 变化必须生成新的规则版本。
- 阈值来源限定为固定依据、经验初值、滚动校准或已验证证据；默认是经验初值。
- 硬否决优先于总分，风险字段缺失不能按安全处理。
- 有效覆盖率达到 90% 且证据一致才允许高置信度；70% 至 89% 为中；更低或关键缺失为低或数据不足。
- 无法从公开数据可靠判断的主体身份、动机和意图不得进入自动评分。

## 首期验收

- 327 个 `QTS-*` ID 全部进入覆盖清单，第 01 章 46 条全部有 YAML 定义和执行 trace。
- 固定 fixture 的规范化输入与结果可重复计算出相同 SHA-256。
- 未知 evaluator、非法状态、阈值无来源、文档漂移、输入篡改和证据篡改会失败。
- PR workflow 不访问网络；盘后 workflow 无论正常、降级或数据不足都保留证据 Artifact。
- 首期所有规则状态最高为 `defined`，没有无证据的 `validated`。
