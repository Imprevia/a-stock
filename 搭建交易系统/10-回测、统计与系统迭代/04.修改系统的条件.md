# 4.修改系统的条件

系统迭代不是看到亏损就改参数，而是在有足够证据时，针对明确问题做最小修改，并重新走验证流程。否则每次改动都会破坏样本可比性，使系统长期处于未经验证状态。

## 一、哪些条件支持修改系统

| 条件 | 应看什么证据 | 可能说明什么 |
|-|-|-|
| 足够样本显示期望显著恶化 | 滚动期望、盈利因子、回撤、分环境表现及置信区间 | 原有优势可能衰减或失效 |
| 制度或交易机制变化 | 交易规则、涨跌幅限制、成交制度、监管和市场结构变化 | 旧规则可能无法执行或统计口径失真 |
| 实际成本持续高于假设 | 实盘滑点、手续费、冲击成本与回测假设差异 | 理论优势无法转化为净收益 |
| 规则存在客观歧义 | 不同执行者/不同时间对同一信号判断不一致 | 规则不可复现，需要重新定义 |
| 账户规模变化 | 成交占比、盘口深度、冲击成本、策略容量 | 仓位扩大后原结果不可复制 |
| 发现未覆盖的系统风险 | 极端行情、相关性上升、流动性枯竭、连续无法退出 | 原风控存在结构性缺口 |

## 二、什么不能成为修改理由

- 连续几笔亏损，但仍在历史正常连亏与回撤范围内；
- 几笔短期盈利，就认为应放大仓位；
- 看到近期行情后临时增加参数，让历史曲线更漂亮；
- 因一次错过机会而放宽全部过滤条件；
- 因违规交易亏损而错误修改核心系统；
- 没有保留旧版本、样本和修改原因，直接覆盖规则。

## 三、正确的修改流程

```text
发现异常 → 判断是数据、执行、环境还是规则问题
→ 提出单一修改假设 → 固定旧版本与基准结果
→ 在训练数据上修改 → 用独立样本验证
→ 模拟/小资金观察 → 达标后切换版本
→ 设置暂停和回滚条件
```

尽量一次只改一个核心因素；若同时改入场、退出、仓位和过滤器，结果即使改善，也无法知道哪项修改真正有效。

## 四、变更控制模板

```text
旧版本 / 新版本：
异常证据与样本量：
问题归类：数据 / 执行 / 环境 / 规则 / 风控
本次唯一修改：
不修改的部分：
样本外验证区间：
通过标准：
暂停与回滚条件：
生效日期：
```

## 五、最终能得到什么

通过严格条件和版本控制，可以区分正常回撤与系统失效，避免追涨杀跌式调参；同时保留可复查的证据，让每次迭代都能回答“为什么改、改了什么、是否真的改善”。

**结论：**先降风险，再查原因；先验证修改，再切换版本。系统迭代应提高可执行性和稳健性，而不是只优化历史收益曲线。

本文用于交易研究与复盘，不构成投资建议。
