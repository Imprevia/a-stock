## Context

补齐入口是 `POST /api/trading-pnl/evidence/fuyao`。现有流程先计算所缺的持仓估值，再通过 Fuyao 客户端查询。客户端的配置、权限、网络、业务拒绝等错误进入适配器后大多折叠成 `fuyao-history-unavailable`。线上这次失败没有可用的上游错误码。现有后端测试使用带自定义回显字段的成功数据，与 [Fuyao 官方响应示例](https://fuyao.aicubes.cn/docs/api-reference/prices/#历史-k-线) 有差异。

## Goals / Non-Goals

**Goals**

- 在适配器内把返回的 K 线绑定到明确的单股、不复权日线请求，让校验结果能追溯到本次请求。
- 在现有 `missing_closes[].reason` 中表达具体的缺项原因，并通过现有前端映射呈现中文。
- 流水覆盖、估值保存、按日期重算和并发控制继续沿用现有台账流程。

**Non-Goals**

- 估值来源扩展、公司行动与停牌证据自动补齐，以及后台历史采集均在本次范围之外。

## Decisions

1. 仅通过官方单股端点请求 `thscode`、`interval=1d`、`adjust=none` 和明确的上海日期毫秒边界，继续使用现有共享传输层和预算。该端点保证单股语义，允许用明确的请求参数绑定没有回显字段的成功响应。
2. 接受含 K 线列表的官方成功响应。响应级回显与请求冲突时拒绝整份历史响应。若仅单行给出冲突的证券或口径，拒绝该行日期的证据，保留其他可独立验证的行。继续按上海日期从 `date_ms` 取值、拒绝同日重复候选，并通过估值模型校验正数和有限性。失败响应和无效行情均保留缺口。
3. 沿用 `fuyao-invalid-history`、`fuyao-close-missing` 和 `fuyao-history-unavailable`，分别对应上游响应无效、请求成功但当日无可用价、网络或服务暂不可用。另增 `fuyao-history-rejected`、`fuyao-history-permission` 和 `fuyao-history-rate-limited` 表达参数或业务拒绝、凭据或权限问题、限流或请求预算耗尽。使用已有异常类型及可获得的结构化上游状态区分原因，遇到共享客户端缺少结构化信息时只补充所需的元数据，保留现有调用方的错误捕获及重试行为。若一份响应含可接受的行和受冲突影响的日期，通过应用端口保留逐日诊断，沿用现有 `missing_closes` 结构返回。
4. 适配器记录单次补齐失败的结构化诊断，包含日期范围、证券、原因和可获得的 HTTP 状态、业务码及经脱敏的请求标识。日志采用字段白名单。界面使用归类后的原因文本。

## Risks / Trade-offs

- 历史响应不回显证券与复权参数 → 仅按明确参数绑定官方单股接口响应，严格处理冲突回显及重复、越界和无效行。固定样本覆盖官方响应结构及负例。
- 原始线上失败缺少上游诊断 → 这两处契约偏差可以离线复现。真实凭据是否具备日线权限、2026-01-21 是否实际返回收盘价，留作经独立授权的盘后只读探测。

## Migration Plan

使用固定响应和隔离 PostgreSQL 验证，再按正常发布流程发布应用。台账结构保持兼容。上线后可由用户在月历手动重试所缺日期，或从已核实的本地行情导入。应用回滚保留已核实入库的估值证据。
