## Context

Vue Router 已用独立路由承载数据采集和偏好设置，FastAPI 以独立 router 汇总 HTTP 资源，后端运行时使用 PostgreSQL。`TradingDayResolver` 从本地证据取得精确的上一交易日。`sector_security_daily_facts` 有原始收盘字段和日期、证券、来源版本，现有采集路径的覆盖取决于板块和历史数据范围，不能当成完整的个人持仓行情库。现有复权数据路径也未证明能供台账识别所有必要的公司行动。功能范围见 [proposal.md](proposal.md) 和 [交易盈亏日历规格](specs/trading-pnl-calendar/spec.md)。

## Goals / Non-Goals

- 保持单用户、单台账部署，使用独立的台账数据与 HTTP 路由。模块的数据和计算可以随台账与估值证据复算。
- 手机和桌面访问同一份台账，移动端能独立完成上传、核对和确认。解析使用运行环境内的 OCR，首版依据已提供的模拟交易版式验证。
- 首版覆盖人民币 A 股模拟交易及盘后估值。自动交易、券商实时连接、跨用户隔离属于本设计范围之外。

## Decisions

### 1. 独立台账路由和 PostgreSQL 事务

在侧栏使用独立入口，建议路径为 `/trading-pnl`、`/trading-pnl/day/:date` 和 `/trading-pnl/import`。月历在每一格显示日期和状态或金额，窄屏允许格内分行。移动导入核对使用原图对应行的预览和纵向表单。Vue 路由直接保留选中的月份或日期，使用浏览器返回也能恢复上下文。

FastAPI 增加 `/api/trading-pnl` 路由组，GET 提供单月摘要和同一交易日的明细，POST 分别处理图片草稿、提交、覆盖确认和记录更正。月视图的查询上限为一个自然月，逐日流水稳定排序并有分页边界。应用层分开读查询、导入命令和纯盈亏计算，PostgreSQL repository 管理台账事务。单用户模式无需将个人信息或用户标识写进每条记录。同一数据库使导入、流水和重算标记原子提交。浏览器本地存储方案的持久数据受设备约束，会让手机补录和桌面复盘分流。

### 2. 图片导入与行级核对

图像上传和识别发生在草稿阶段。限制文件数量、大小、解码像素和识别时长。暂存原图、只在草稿核对时读取，对解码失败和处理超时返回可重试状态。候选行保留图片与行位置、原始识别结果、解析结果和待核字段。确认或草稿到期后清理原图和不必要的识别原文，正式记录保留图片摘要、行级引用、确认值与决策。批次在日志中用不透明 ID 引用。实际截图用于说明版式，仓库测试素材由同结构的合成数据生成。

首版解析月份分组标题和组内 `MM-DD`，处理 `603019.SH` 形式的证券代码、股份、单价、金额与交易状态。上下文被裁切时由用户补齐年份或月份。手机状态栏、月份汇总和账户摘要各自保留为对应类型。`今日盈亏` 的采集日及估值时点无证据时，只用于预览诊断。识别出的完成成交额可与价格和股数核对。买卖方向、委托状态、实际成交数量及已知的成交编号和委托编号分别保存。撤单行只在已确认取消全部未成交数量时按零成交处理。部分成交、连续状态更新和拆分成交需要识别对应委托或由用户确认关联，累计成交量只贡献已确认的增量。

采用运行环境内的中文 OCR 及确定性版式解析器，优先验证目标运行环境可用的 Tesseract 中文模型及版式样本。云端视觉识别需要传送截图，个人台账的图片处理留在本地即可满足当前工作流。

### 3. 按证据强度处理重复记录

- 原始文件哈希用于识别完全相同的图。批次、图像、行身份用于重复草稿或重复确认的重放。交易所或来源的稳定编号按其明确的作用域保存，区分成交身份、委托身份和状态事件身份，同一编号出现不同已确认字段时进入核对。
- 无成交编号的候选使用精确日期、规范证券和方向筛选，结合已知时间、数量、价格、金额、状态与行位置给出可能匹配。即使可见字段完全一致，也可由用户把两笔独立交易分别保留。候选比较覆盖同批其它行与此前确认台账。行指纹只用于检索和提示。
- 确认携带一次性操作键、草稿版本及疑似重复的处理决策。事务内锁定台账修订标记，重新校验正文摘要、选择、当前候选与强身份唯一约束。相同操作键与相同确认内容回放之前结果，键与正文冲突或候选变化时返回冲突。事务同时提交确认流水、审计事件和重算起点。仅依靠前端禁用按钮无法处理两个浏览器同时提交。

### 4. 历史回放、日历覆盖和更正

由单用户显式配置已确认期初 2026-01-20 收盘空仓，自 2026-01-21 开始按上海交易日回放。数据库迁移只建立结构。将期初、确认成交、委托事件、独立调整和用户确认的日期覆盖分别存储。范围确认与逐日「无成交」使用同一语义，导入程序可提示月份笔数是否一致，最终覆盖仍依赖用户确认。先录入的部分流水可查看。遇到未确认范围和无法验证的持仓变化时，从首个受影响交易日将持仓连续性标为不足。后续补录解除缺口后顺序重建。

采用可回放的交易流水和按日期索引的持仓投影。更正保留版本与审计，影响日期的完整性确认随更正重新核对，可在同一操作中明确重确认。自最早受影响的交易日重建后续持仓及日级统计。应用在改动事务内记录失效起点。未完成重建的日期呈现待重算，月历和日期明细只发布同一已验证台账修订的结果。投影计算可在显式入账或更正流程中完成，读取使用当前本地事实。逐次从期初把全量交易装入查询的方案会放大历史越久时的读取成本。

### 5. 盘后估值数据与费用版本

公式以相邻真实交易日的原始收盘持仓市值差为起点，计入当天净卖出、含费买入和有依据的应计调整。期初空仓市值为零。当日完全卖空的证券只需其上一交易日收盘市值，当日新增持仓需要当日收盘价。持仓按实际成交和可验证的送转数量更新。分红以权利确认及应收金额计入一次，付款日冲销应收，避免重复入账。停牌估值只接受有日期和依据的正式结算估值。账外资金流独立标记，排除在交易和持仓盈亏外。

价格读取优先复用已有 `original_close` 与对应的来源、日期、证券身份及质量信息。实现先核对覆盖，缺口通过显式、可审计的本地行情证据导入或仓库现有获准盘后采集路径补齐。公司行动适用性或内容缺失时，收盘价可在明细独立展示，受影响总盈亏保留缺项。后续批准的数据写入可补齐估值证据，月历 GET 使用已有本地证据和持仓投影，不创建采集任务。购买证券所用的公开行情查询范围与个人流水始终分开。

金额使用十进制定点数，并以统一规则输出分。对已确认的独立成交，缺实际佣金时按 `max(成交额 × 0.00025, 5.00)` 计算并按四舍五入到分。具有明确共同收费单位的多笔部分成交先汇总，再应用一次最低收费。收费单位未知时标为待核。实际记录确认的佣金优先。首版默认计算已明确的模拟佣金，实际卖出税费或其他费用以有证据的金额补录并单独列示。已知某项费用发生但金额未知时，标记缺项。费用来源、规则版本、确认状态和行情来源随估值明细返回。期初样本两行应各收 ¥5，买入合计 ¥19,621.00，可独立验证佣金和持仓重建。

## Risks / Trade-offs

- 同向同量同价成交会与重叠截图相似 → 自动查重依赖强身份，其余展示并由用户确认。
- 截图常被截断，券商 App 的月份笔数可能含有撤单 → 记录笔数与覆盖确认独立，按行状态核对实际成交。
- 历史个股收盘或公司行动证据可能不全 → 明细保留已确认记录和具体缺项，待补齐后复算受影响日期。
- 现有部署没有平台账户认证 → 台账部署沿用个人访问范围，真实截图仅在个人运行环境中暂存和识别，运行日志及公共市场数据发现页保持汇总级信息。

## Migration Plan

1. 实施前新增 active plan，补齐产品规格、架构、运行手册和代码到文档的映射。
2. 增量 Alembic 迁移建立个人台账结构，在隔离 PostgreSQL 应用迁移并验证事务和重试。验证本地 OCR 的运行依赖和可读的合成图片。
3. 在个人环境显式设置 2026-01-20 期初空仓。按月份上传展开的交易截图，核对流水及覆盖，再用授权数据路径补齐收盘和公司行动证据。
4. 应用版本回退时先结束导入操作，保留已确认流水、图片哈希和日级证据，按仓库既有流程备份。个人环境外的迁移、行情补采和发布沿用仓库运行授权。
