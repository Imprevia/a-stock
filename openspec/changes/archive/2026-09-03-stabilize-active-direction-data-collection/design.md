## Context

容量方向是 `activeDirection` 独立数据集，使用东方财富股票列表接口按成交额 `f6` 降序请求 100 行，再从前 30 行计算行业聚集、展示前 10 只股票。现有实现对证券代码、名称、成交额、最小 30 行样本和排序执行校验，但只请求 `https://push2.eastmoney.com/api/qt/clist/get`；主域在当前网络环境中经过共享客户端的有界连接重试后仍出现 `RemoteDisconnected`，最终写入 `failed-missing`。

行业采集已经建立相同供应商的 `push2` 到 `push2delay` 降级模式。2026-09-03 的只读复现表明，容量方向使用原参数请求延迟域时，接口报告 5908 个总样本、返回 100 个有效 Top-N 样本、保持成交额降序，并为前 30 行提供完整行业字段。仓库现有 SQLite、collection coordinator、共享东方财富串行 limiter 和精确日期保留机制无需改变。

## Goals / Non-Goals

**Goals:**

- 在容量方向主域恢复失败后使用已验证的同口径延迟域。
- 对两个端点使用相同的必需字段、最小样本和排序校验。
- 准确记录主域或延迟域来源、质量状态和主域失败 warning。
- 保持同日期成功快照保留、失败任务审计和历史日期隔离。
- 用离线测试锁定降级与无效载荷行为，并以显式本地命令执行真实数据 smoke test。

**Non-Goals:**

- 不引入东方财富之外的独立容量方向数据源。
- 不提供容量方向历史回补，也不把最新快照标记为历史日期数据。
- 不改变 Top-30 行业聚集、Top-10 展示或候选方向判定算法。
- 不调整东方财富共享 limiter、重试预算、SQLite schema、公开 API 路径或业务字段。
- 不修改前端交互；现有页面继续消费相同数据和质量契约。

## Decisions

### 1. 容量方向使用主域到延迟域的确定性降级链

provider 先请求 `push2` 主域。主域在共享 `EastmoneyClient` 的有界恢复后仍发生连接、HTTP、JSON 结构或业务载荷失败时，再使用完全相同的查询参数请求 `push2delay`。延迟域通过校验后返回数据；只有两个端点都失败时，外层容量方向入口才生成 `failed` 质量结果。

替代方案是依赖人工重试主域，但盘后定时采集会反复产生部分批次，且同一批次行业已经证明延迟域可用。另一个方案是立即引入腾讯或通达信独立备胎，但它们不能在一次稳定请求中同时提供全市场成交额 Top-N 和现有行业字段，会扩大数据拼接与一致性范围。

### 2. 抽取按 URL 获取并校验 Top-N 的单一路径

将当前容量方向 HTTP 请求和响应校验形成按 URL 调用的内部边界，主域与延迟域都经过同一逻辑：接受列表或键值对象形式的 `data.diff`，筛出具有代码、名称和成交额的对象，要求至少 30 个有效样本，并验证成交额非递增排列。延迟域不得使用较弱校验或在本地重新排序后掩盖上游乱序。

替代方案是在主域和延迟域各复制一份解析逻辑，但字段或阈值变化时容易产生不一致，无法证明两个来源满足同一契约。

### 3. 构建函数接收来源、状态和 warnings

当前容量方向构建函数把 `source=\"eastmoney-clist\"` 和 `status=\"partial\"` 写死。它应像行业构建路径一样接收来源、状态和 warnings：主域成功保持 `eastmoney-clist` / `partial`；延迟域成功使用 `eastmoney-clist-delay` / `fallback`，并在既有“连续性指标尚未接入”warning 之前保留主域错误和降级说明。

不新增响应字段，因为现有 `quality` 已能表达来源、状态和 warnings；新增字段会产生不必要的 schema 和前端兼容成本。

### 4. 失败保留继续由 collection coordinator 和 snapshot store 负责

两个端点都失败时，provider 返回 `status=failed`、空 `topStocks` 和组合后的主域/延迟域错误。collection coordinator 继续依据是否存在相同 `dataset/as_of` 成功快照记录 `failed-retained` 或 `failed-missing`。provider 不自行读取 SQLite，也不跨层决定快照保留。

这样保持 provider、编排和持久化的既有所有权边界，并避免容量方向形成特殊存储路径。

### 5. 网络 smoke test 不进入确定性测试门禁

单元测试使用固定响应和异常注入验证主域成功不调用延迟域、主域失败后降级、延迟载荷无效、双端点失败和质量元数据。实施完成后使用当前上海市场日执行单数据集真实采集，确认 `eastmoney-clist-delay` 能保存为成功 fallback；该网络结果写入 plan 证据，但不成为离线 pytest 的依赖。

## Risks / Trade-offs

- [主域和延迟域属于同一供应商，可能同时不可用] -> 两个端点均失败时明确记录失败并只保留同日期旧值，后续若需要更高可用性再单独设计独立供应商方案。
- [延迟域盘中数据可能落后于主域] -> 质量状态固定为 `fallback` 并保留来源；系统只把它视为当前市场日快照，盘后调度仍是正常采集路径。
- [延迟域字段或排序规则发生变化] -> 在保存前执行与主域相同的必需字段、最小样本和排序校验，失败时不覆盖旧快照。
- [简单替换 URL 会把降级数据标成主域] -> 参数化构建质量元数据，并增加精确断言防止来源和 warning 回归。
- [当前工作区还有盘后调度的进行中改动] -> 新 change 仅增量修改容量方向 provider、相关测试和事实源文档，不回退或重写调度实现。

## Migration Plan

1. 创建 active exec plan，并先更新产品规格、架构、runbook 和状态中的容量方向降级契约。
2. 抽取容量方向按 URL 获取和统一校验边界，实现主域到延迟域的降级链。
3. 参数化容量方向构建结果的来源、状态和 warnings，保持现有业务字段兼容。
4. 增加 provider 与 collection/snapshot 的离线测试，覆盖成功、降级、无效载荷和失败保留。
5. 运行聚焦及全量 pytest、OpenSpec strict、docs-contract full 和 `git diff --check`。
6. 对当前上海市场日执行显式容量方向真实采集并记录结果；回滚时恢复单主域调用，SQLite 无需迁移或删除。
